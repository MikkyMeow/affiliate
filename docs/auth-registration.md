# Аутентификация и подтверждение почты

## Общая логика

- Пользователь регистрируется, аккаунт создаётся, поле `email_verified_at` остаётся `null` до подтверждения.
- После регистрации автоматического входа нет: API возвращает сообщение о том, что на почту выслано письмо, и фронт должен показать экран «Письмо отправлено, подтвердите email».
- Логин запрещён, пока `email_verified_at` пуст; backend возвращает ошибку `EMAIL_NOT_VERIFIED`, чтобы фронт мог показать понятное сообщение и нужную кнопку.
- Потоки восстановление пароля и повторной отправки письма всегда отвечают одинаково вне зависимости от существования аккаунта, чтобы не раскрывать, зарегистрирован ли email.
- Токены для подтверждения и сброса хранятся в отдельной таблице `user_action_tokens`, записываются как хэши, имеют TTL (24 ч для верификации, 1 ч для сброса), после использования помечаются `used_at`, а повторное применение возвращает понятный код ошибки.

## `POST /api/v1/auth/register`

### Тело запроса

| Поле         | Тип     | Обяз. | Описание                                                                 |
|--------------|---------|-------|--------------------------------------------------------------------------|
| `email`      | string  | да    | Логин пользователя (уникально в `users` и `affiliates`).                 |
| `password`   | string  | да    | Пароль, минимум 8 символов.                                              |
| `name`       | string  | да    | Отображаемое имя / название сущности.                                    |
| `accountType` | string | да    | `affiliate` или `advertiser`.                                            |

> `name` временно используется как `displayName` пользователя и как `name`  
> для созданной сущности `affiliate`/`advertiser`. Остальные поля появятся позже.

### Поведение

- Создаётся пользователь, email помечается как неподтверждённый, и в `user_action_tokens` создаётся одна запись `type = 'email_verification'`.
- Сразу отправляется письмо с ссылкой на фронтовую страницу (`EMAIL_VERIFY_URL_BASE + ?token=...`).
- Автоматического логина нет — пользователю нужно подтвердить почту через письмо.

### Ответ

```json
{
  "success": true,
  "message": "На указанный email отправлено письмо. Подтвердите почту, чтобы войти."
}
```

Фронт показывает инструкцию и, при необходимости, кнопку «Отправить письмо повторно».

## `POST /api/v1/auth/login`

- При попытке логина пользователь проверяется по email и паролю.
- Если `email_verified_at` ещё `null`, возвращается `403` или `401` с кодом `EMAIL_NOT_VERIFIED` и текстом «Почта не подтверждена. Проверьте письмо или запросите повторную отправку».
- Дальше поведение остаётся прежним: `issueAuthPackage` выдаёт JWT и `refresh_token`.

## `POST /api/v1/auth/resend-verification`

- Принимает `email`.
- Если аккаунт с таким email существует и email ещё не подтверждён, генерирует новый токен `email_verification` и отправляет письмо.
- Ответ всегда единообразный (`200` + сообщение о том, что письмо отправлено), независимо от того, существует ли пользователь или нет.

## `GET /api/v1/auth/verify-email?token=...`

- При получении токена проверяется хэш по таблице `user_action_tokens`, срок действия (24 ч) и флаг `used_at`.
- Токены хранятся только в виде хэшей, а поле `used_at` заполняется при валидной проверке.
- Успешная проверка устанавливает `email_verified_at` и возвращает редирект/сообщение.
- При невалидном, просроченном или уже использованном токене отправляются коды `TOKEN_INVALID`, `TOKEN_EXPIRED` или `TOKEN_ALREADY_USED`.

## `POST /api/v1/auth/forgot-password`

- Принимает `email`.
- Если аккаунт существует — создаёт одноразовый токен `password_reset`, отправляет письмо с `PASSWORD_RESET_URL_BASE + ?token=...`.
- Ответ всегда одинаковый: `{"success": true, "message": "Если аккаунт существует, письмо отправлено"}`.

## `POST /api/v1/auth/reset-password`

- Принимает `token` и `newPassword`.
- Находит хэш токена (`password_reset`), проверяет TTL 1 ч и `used_at`.
- Если всё валидно — обновляет `password_hash`, помечает токен использованным и возвращает `200`.
- При ошибках возвращаются коды `TOKEN_INVALID`, `TOKEN_EXPIRED` или `TOKEN_ALREADY_USED`.

## Коды ошибок в новом потоке

- `EMAIL_NOT_VERIFIED` — email существует, пароль верный, но почта не подтверждена.
- `TOKEN_INVALID` — токен не найден или хэш не совпадает.
- `TOKEN_EXPIRED` — прошёл TTL (24 ч для верификации, 1 ч для сброса).
- `TOKEN_ALREADY_USED` — токен уже применялся и помечен `used_at`.

Фронт должен полагаться на коды, а не на текст ошибки, чтобы показывать нужный экран (запрос повторной отправки, форма нового пароля и т.п.).
